PRUEBA HM-10: confirmar que el discovery funciona pero el manufacturer-data
llega vacío para el SmartSolar (mismo resultado que se obtuvo en la sesión
del 2026-08-04).

Requisitos:
- HM-10 conectado por el adaptador USB-serial (FT232), típicamente en /dev/ttyUSB0.
- Ejecutar todo esto en una terminal de Linux, en la PC donde está conectado el módulo.
- El SmartSolar tiene que estar encendido y en rango.

-----------------------------------------------------------------------------
PASO 0 - Confirmar el puerto y dejarlo en 115200 baudios, modo raw
-----------------------------------------------------------------------------

ls -la /dev/ttyUSB*

stty -F /dev/ttyUSB0 115200 raw -echo cs8 -parenb -cstopb -crtscts

-----------------------------------------------------------------------------
PASO 1 - Función auxiliar para mandar un comando AT y leer la respuesta
-----------------------------------------------------------------------------

Pegar esto tal cual en la terminal (define una función, no hace nada todavía):

send_at() {
  local cmd="$1"
  local wait_s="${2:-1.5}"
  local out="/tmp/at_out.txt"
  : > "$out"
  timeout "$wait_s" cat /dev/ttyUSB0 > "$out" &
  local catpid=$!
  sleep 0.2
  printf '%s' "$cmd" > /dev/ttyUSB0
  wait $catpid 2>/dev/null
  echo "[$cmd] -> $(cat "$out" | tr -d '\0')"
}

-----------------------------------------------------------------------------
PASO 2 - Verificar que el modulo responde y ver firmware/rol
-----------------------------------------------------------------------------

send_at "AT"          # comando de test: confirma que el modulo esta prendido y escuchando al baudrate configurado
send_at "AT+VERR?"    # pide la version de firmware del modulo
send_at "AT+ROLE?"    # consulta el rol BLE actual: 0 = Peripheral (se deja encontrar), 1 = Central (busca a otros)

Se espera:
[AT] -> OK
[AT+VERR?] -> HMSoft V608
[AT+ROLE?] -> OK+Get:1        (1 = Central, ya seteado de antes)

Si AT+ROLE? da 0 (Peripheral), correr:
send_at "AT+ROLE1"    # fuerza el modulo a modo Central; sin esto no puede escanear otros dispositivos
send_at "AT+RESET" 2  # reinicia el modulo para que el cambio de rol tome efecto

-----------------------------------------------------------------------------
PASO 3 - Confirmar IMME (esto es lo que faltaba la primera vez)
-----------------------------------------------------------------------------

send_at "AT+IMME?"    # consulta el modo "immediate": 0 = al resetear arranca solo en modo trabajo (bloquea usar comandos de escaneo), 1 = espera comandos AT

Si da OK+Get:0 hay que cambiarlo a 1 y resetear:

send_at "AT+IMME1"    # pone IMME en 1 - esto es lo que faltaba para que el escaneo funcionara
send_at "AT+RESET" 2  # reinicia para que el cambio de IMME tome efecto
sleep 1
send_at "AT"          # confirma que el modulo volvio a responder despues del reset
send_at "AT+ROLE?"    # reconfirma que sigue en modo Central (1) despues del reset
send_at "AT+IMME?"    # reconfirma que IMME quedo en 1 despues del reset

Se espera OK+Get:1 en ROLE e IMME despues de esto.

-----------------------------------------------------------------------------
PASO 4 - Lanzar discovery y pedir los resultados (AT+DISI?)
-----------------------------------------------------------------------------

send_at "AT+DISC" 6   # dispara un escaneo BLE de 6 segundos; no imprime nada directo, guarda los resultados adentro del modulo
send_at "AT+DISI?" 1  # pide la lista de dispositivos que encontro el ultimo escaneo

Formato de cada linea de resultado:
OK+DISC:<manufacturer_id>:<manufacturer_data>:<otro_campo>:<MAC>:<RSSI>

Buscar la MAC del SmartSolar: CBEA5B96336C

Resultado que se obtuvo (y el problema que confirma):
OK+DISC:00000000:00000000000000000000000000000000:0000000000:CBEA5B96336C:-064

O sea: la MAC aparece, el RSSI es real (varia entre corridas), pero
manufacturer_id y manufacturer_data vienen en CEROS. En una corrida previa
apareció un dispositivo (un iBeacon) con datos reales en ese mismo campo,
por ejemplo:
OK+DISC:4C000C0E:003B2BC9F893E798DE43F6C4B9001005:301C7F84EB:<mac>:-077
— pero no es algo que vaya a aparecer siempre; depende de qué dispositivos
BLE haya cerca en el momento del escaneo. Si en tu prueba TODOS los
dispositivos salen en cero (como pasó en la corrida del usuario), no es un
problema — solo significa que no había ningún dispositivo tipo iBeacon
cerca. Lo que importa para la conclusión es únicamente la fila del
SmartSolar, no la comparación con otros.

Repetir el paso 4 dos o tres veces (send_at "AT+DISC" 6 de nuevo) para
confirmar que no es casualidad - el RSSI del SmartSolar debe variar entre
corridas (prueba de que lo está detectando en vivo) mientras el
manufacturer_data se mantiene siempre en cero.

-----------------------------------------------------------------------------
PASO 5 (opcional) - Probar tambien AT+DISC? (formato distinto, con nombre)
-----------------------------------------------------------------------------

send_at "AT+DISC?" 6  # variante de escaneo que ademas devuelve el nombre BLE de cada dispositivo (formato DIS1/RSSI/NAME, distinto al de DISI)

Este formato es distinto (DIS1 / RSSI / NAME) y sí muestra el nombre del
dispositivo ("SmartSolar HQ2248DRUEV"), pero tampoco expone manufacturer
data cruda. Sirve para confirmar identidad del dispositivo, no para
resolver el problema.

-----------------------------------------------------------------------------
CONCLUSION QUE SE BUSCA CONFIRMAR
-----------------------------------------------------------------------------

El HM-10 (firmware HMSoft V608) SI detecta el SmartSolar (MAC visible, RSSI
real). El problema es que el campo de manufacturer-data que trae el
advertisement de Victron (necesario para descifrar los datos de Instant
Readout) llega siempre en cero - el firmware del modulo no lo expone. Por
eso no sirve para este proyecto, mas alla de que "encuentre" el dispositivo.
